# Shared online member profile

Profile edits queue an owner-scoped `planning_documents` save through the existing revision-checked `save_planning_document` RPC. For an authenticated profile only, browser quota failure keeps the edit in memory and permits cloud saving. The last durable device copy is retained; stale-tab and account-generation checks still apply. Cloud success preserves the server revision even when the device cache remains full. A failed upload remains pending, warns before leaving, and exposes Retry rather than claiming a local or online save.

Photos are rasterized to at most 512px, then sent through `/api/profile/photo` to the website's fixed `/api/app/profile-photo` service. Both verify the member bearer token. The existing website uploader validates PNG/WebP bytes, strips metadata, writes only the authenticated member's avatar path, and updates shared auth metadata. No app service-role credential or additional bucket is needed. The app stores the small returned URL. Existing embedded profile photos migrate on the next successful profile save.

After the planning server confirms the save, the profile UI mirrors only display name and avatar fields into account metadata. The website refreshes only these display fields when reading its verified session; identity, role, entitlements and expiry are preserved. Website avatar timestamps allow the app to adopt a newer website photo without replacing pending app edits. Full health/preferences remain private in the existing planning document, not in auth metadata.

Release requires both repositories: app changes plus website `src/app/api/app/profile-photo/route.ts`, `src/lib/shared-member-identity.ts`, `src/lib/client-auth.ts`, and the avatar timestamp additions in `src/lib/member-avatar.ts`. Existing environment variables and avatar bucket are reused; no SQL migration is required. These changes are local until deployment. Verification uses isolated fake accounts, not a real member write.
