Workout plans allocate 100 progress points per scheduled session plus four 25-point support checkpoints/week. Nutrition plans allocate at most 25 points/day for a meal practice, 25/day for hydration, and 50/week for a review, totaling four levels/week. More eating, drinking, logging or repeated workouts cannot create additional scheduled points. Points are separate from spendable bolts.

There are 1,672 activities and 776 fixed reward slots. Ordinary levels contain 50 coins, 5 bolts or 1 sapphire/topaz/ruby. Every fifth level has a globally distinct milestone design identity. Emeralds are excluded from the common pool because real-service redemption needs its own economics. Current milestone names are unique calendar/avatar atmosphere design briefs, not finished assets or the older illustrative 60-item wardrobe draft.

## What is wired

- App My Plan reads lightweight summaries, then fetches the selected frozen definition on demand.
- Website Admin → Training → Member Programs and Client Hub → Resources read the same database.
- Every scheduled activity contains a signal title, action and evidence requirement.
- Dashboard level, meter and reward track read the active shared enrollment and verified credits. With no enrollment, level remains a dash and no level emblem appears. At enrollment level zero is shown, without a Roman numeral emblem.
- The training signal includes all checkpoints from an active shared program, marked completed only when an activity credit exists.
- Account changes invalidate pending progress reads; an old account's result cannot populate the next account's dashboard.
- Database RLS isolates enrollments and credits. Clients cannot insert progress or mutate plan versions. Enrollment accepts only published versions; one active enrollment per member prevents accidental simultaneous tracks.

## Still incomplete — not a production-ready enrollment flow

All initial definitions have **review** status. They are structured starter templates, not completed individualized prescriptions or approved Academy publications. Several related goals share a starting exercise framework; PR and nutrition variants need further goal-specific programming rather than relying on their different titles alone.

Milestone cosmetics have `fulfillment: design`. The database refuses publication while any reward asset is unfinished. Actual wearable/background assets and equip/entitlement fulfillment are still required.

The current enrollment RPC is groundwork. A member-facing selection/start-date flow must still enforce saved profile/goals and turn the program activities into executable weekly assignments/templates. A server evidence adapter must bind those exact assignments to saved workout/meal/hydration/review records, award credits idempotently, and atomically fulfill level rewards through the existing wallet/inventory services. **No completion-award RPC exists yet**, so clients cannot fabricate points while those adapters are unfinished. Existing local weekly plans are intentionally not treated as shared catalog enrollments.

## Authoring and updating

Do not update an existing `(program_id,version)`. Author v2 and preserve v1 for enrolled members. Rewards are allocated once and stored in the definition; runtime reads do not reroll them. The sync script refuses an existing version whose contents differ.

`scripts/sync-shared-programs.cjs` is read-only by default. `--apply` inserts absent versions in a transaction and never overwrites existing definitions. Run with the website's environment and installed `postgres` module; never commit credentials. Future authoring tooling should call this shared backend rather than migrate content separately between the platforms.

Validation: `node --test scripts/test-shared-programs.mjs scripts/test-program-rewards.cjs`. The SQL suite exercises immutable versions, unfunded budgets, unpublished assets, blocked review enrollment and denied client credit writes. It does not imply that the unfinished live award/equip flow has been tested.
